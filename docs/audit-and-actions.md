# Audit And Action Workflow

## 한국어 요약

이 프로젝트의 Action Workflow는 **자동 복구 실행 기능이 아니라 안전한 운영 절차를 기록하는 기능**입니다.

현재 Platform과 Node Agent는 운영 환경을 직접 변경하는 작업을 실행하지 않습니다. RCA report가 추천 조치를 만들면 사용자는 action request를 생성하고, 승인자는 승인/거절을 기록합니다. 승인 이후에도 실제 처리는 사람이 runbook 또는 GitOps PR로 진행하고, Platform에는 `complete-manual`로 완료 사실만 기록합니다.

Audit log는 이 플랫폼의 핵심 기능입니다. 장애 원인뿐 아니라 “누가 어떤 판단을 했고, 어떤 export나 approval을 수행했는지”를 남겨야 엔터프라이즈 환경에서 설명 가능한 운영이 됩니다.

## Current Action Model

Recommended actions are generated by the RCA analyzer and classified by the Policy Engine.

Action categories:

- `AUTO_SAFE`: safe read-only verification only
- `APPROVAL_REQUIRED`: human approval and manual runbook handling
- `GITOPS_PR_ONLY`: change should be reviewed as GitOps PR
- `NEVER_AUTO_EXECUTE`: high-risk operation that must not be automated
- `MANUAL_INVESTIGATION`: investigation-only recommendation

Important rule:

```text
Approval does not execute host commands.
Approval records that a human-operated runbook or external workflow may proceed.
```

## Action Request States

Current manual workflow states:

```text
blocked
pending_approval
approved_manual
rejected
completed
accepted
```

Typical flow:

```text
RCA Report
  -> Recommended Action
  -> Action Request
  -> pending_approval
  -> approved_manual or rejected
  -> completed after external handling
```

For read-only action confirmation, the platform may create an evidence request for additional collection. This is not host mutation.

## Disabled Agent-Side Execution

Agent-side mutation execution has been permanently disabled.

- The previous agent-side action module has been removed.
- Agent runtime no longer creates an action executor.
- `POST /api/agents/action-executions` returns an empty list for compatibility.
- `POST /api/agents/action-results` returns `410 Gone`.
- Legacy queued or leased action execution rows are expired by migration.

The migration `V6__disable_agent_action_execution.sql` expires old execution rows and converts queued/executing action requests to manual handling.

## Audit Events

Audit events should be generated for:

- login success/failure
- logout
- password change
- user approval/rejection
- cluster create/delete
- agent register/auth failure
- webhook ingest
- evidence submit
- report generation
- incident correlation
- report export
- evidence bundle export
- demo scenario run
- action request creation
- action approval/rejection
- manual completion
- notification sent/failed
- retention maintenance completed/failed

## Audit Event Shape

Audit records should include enough context for investigation.

```json
{
  "actor_type": "user|agent|system",
  "actor_id": "operator@example.com",
  "action": "rca.action_request",
  "resource_type": "action_request",
  "resource_id": "action-...",
  "result": "approved_manual",
  "details": {
    "report_id": "report-...",
    "action_key": "manual_runbook_review",
    "policy": "APPROVAL_REQUIRED",
    "source": "rule_based"
  }
}
```

## RBAC Notes

- `ADMIN` and `OPERATOR` can create action requests.
- `ADMIN` and `APPROVER` can approve or reject approval requests.
- `ADMIN` and `OPERATOR` can mark approved manual requests as completed.
- `VIEWER` cannot mutate action workflow.
- `APPROVER` should not export evidence bundles by default.
